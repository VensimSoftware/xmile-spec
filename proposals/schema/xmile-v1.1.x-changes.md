# xmile-v1.1.x-proposal.xsd: what changed and why

`spec/schema/xmile.xsd.xml` plus seven changes. Generated by
`tools/v-generate/make_v11x_proposal.py`; edit the generator, not the schema. Checked by
`tools/v-generate/compare_v11x.py`, which is where the numbers below come from.

**Six of the seven changes are additive**: no document that validates against v1.1 fails
against them, and no file in a 122-model corpus gains an error. The checker asserts that
rather than assuming it — a schema change that fixes one thing and breaks another is not
minimally invasive, whatever its intent.

**Change 7 is deliberately restrictive**, and is the only one. It requires a whole-model
`<dim>` to say what it contains. No file in the corpus is affected, which is what makes it
safe to propose, but it is the change to look at first if a file that used to validate
stops.

Measured over the corpus: **29,407 errors down to 28,000**, 76 files improved, none
worse. The seven changes account for all 1,407.

| # | Change | Item | Errors removed |
|---|---|---|---:|
| 1 | vendor attributes on simple-typed elements | 1 | 36 |
| 2 | `<doc>` on containers and on `<dim>` | 4 | 1 |
| 3 | `<model_dimensions>` for the whole-model list | 3 | 0 |
| 4 | requirements nobody meets become optional | 9's pattern | 1,299 |
| 5 | `<smile>` as a synonym for `<options>` | 11 | 71 |
| 6 | `<license>` in `<header>` | 10 | 0 |
| 7 | a whole-model `<dim>` must be interpretable | 5's pattern | 0 (restrictive) |

Changes 3 and 6 remove no errors because nothing writes what they permit yet. They exist
so that something can.

## 1. Vendor attributes on simple-typed elements

55 element declarations used a built-in type. `defaultAttributes` reaches complex types
only, so none of them could take a vendor attribute, and the schema's extension mechanism
stopped at their boundary.

**Three are rewritten. The other 52 are left alone**, and the short version of why is that
almost nowhere needs it:

| Rewritten | Why |
|---|---|
| `<connector><to>` | The only one with evidence. `vensim:attach` on it is 36 of the 74 vendor-namespace errors that survived the v1.1 schema — half the residue, from one element. |
| `<sim_specs><start>`, `<stop>` | So a control parameter can carry its equation's comment as `vensim:doc`. Vensim's `.Control` group gives each of them one, and `<sim_specs><doc>` holds only the group's. |

Everything else keeps its built-in type:

| Left alone | Why |
|---|---:|
| under `<header>`, 10, and `<contact>`, 5 | Bibliographic metadata. Nothing in the corpus carries an attribute or a child on any of them. |
| `<eqn>`, 6 | Every variable that has one also has a `<doc>`, so `<eqn><doc>` would be a second place to say the same thing. None of the 23,579 occurrences carries an attribute. |
| `<mathml>`, 6 | A MathML payload — foreign markup with its own namespace and its own rules. |
| under `<conveyor>`, 5 | `len`, `capacity`, `in_limit`, `sample`, `arrest`: scalar settings with nowhere to grow. |
| under `<macro>`, 4 | `<parm>`, `<format>` and its own `<eqn>` and `<doc>`; a macro is a function definition. |
| `<doc>`, 4 | A `<doc>` inside a `<doc>` is nobody's idea. |
| `<units>`, 3 | No attribute in 9,129 occurrences; the variable is where anything about it belongs. |
| `<inflow>` and `<outflow>`, 2 each | References to a flow by name. |
| under `<unit>`, 2 | A unit definition's `<eqn>` and `<alias>`. |
| `<multiplier>`, 2 | A flow's unit-conversion multiplier. Four in the corpus, none annotated. |
| `<of>`, 1 | The variable an `<alias>` points at. A name. |

Counts are by the first rule that matches, so a `<macro>`'s `<eqn>` is counted under
`<macro>` rather than under `<eqn>`. They sum to 52, and with the three rewritten to 55.

`NO_REWRITE_UNDER`, `NO_REWRITE_NAMED` and `NO_REWRITE_PAIRS` in the generator hold those
decisions; removing a name brings the element back in.

Each of the three is rewritten as a `simpleContent` extension of the same base:

```xml
<xs:element name="to" type="xs:string"/>
<!-- becomes -->
<xs:element name="to">
  <xs:complexType><xs:simpleContent><xs:extension base="xs:string"/></xs:simpleContent></xs:complexType>
</xs:element>
```

Content is unchanged; the element simply comes inside the extension mechanism.

This started at all 55 and was cut back one group at a time, which is worth recording
because the measurement drove it. Disabling the change entirely and diffing the corpus
shows it is worth **36 errors, every one `vensim:attach` on `<connector><to>`**. Nothing
else in 122 models needs it. So the rewrite goes where there is evidence, plus the two
control parameters where a concrete need was identified and the vendor namespace supplies
the answer — and not on the principle that every built-in type should become extensible.

The counter-argument deserves recording too: `<to>` is a case nobody would have predicted,
and it surfaced only because one vendor happened to need it. A future vendor will want
something equally unforeseeable, and each exclusion here is a place they will not be able
to put it. The generator makes that a one-line decision either way.

## 2. `<doc>` on containers, and on `<dim>`

`<doc>` is added to `<model>`, `<module>`, `<sim_specs>`, `<group>`, the whole-model
`<dimensions>` and `<dim>`: seven declarations, since `<module>` is declared twice.

Only the **whole-model** `<dimensions>` takes a `<doc>`. The per-variable one is a list of
bare name references sitting on a variable that already has a `<doc>` of its own, and
change 3 supersedes it in any case. The two are told apart by structure rather than by
name — the whole-model declaration is the one whose `<dim>` has `<elem>` children — which
is the same collision change 3 addresses, showing up again in a different guise.

### `<dim>` needs its own, and the container's is no substitute

`<model_dimensions>` is the **list**; `<dim>` is one dimension in it, which is one Vensim
subscript range, and each range carries its own comment:

```
Region : North, South, East, West
    ~
    ~   The regions the model distinguishes
```

A model with six subscript ranges has six such comments and one container. One `<doc>` on
the list cannot hold them, so without `<doc>` on `<dim>` they are merged or dropped on
export.

```xml
<model_dimensions>
  <dim name="Region" size="2">
    <doc>The regions the model distinguishes.</doc>
    <elem name="North"/><elem name="South"/>
  </dim>
  <dim name="Product" size="3"><doc>Product lines.</doc></dim>
</model_dimensions>
```

The container keeps a `<doc>` of its own, for a note about the dimension set as a whole.

A vendor attribute would also work — `<dim>` is a `complexType`, so `defaultAttributes`
already admits `vensim:doc` — and that is the right answer for the control parameters,
where the need is ours alone. It is the wrong answer here. Every tool with named subscript
ranges has per-range comments to carry, so this belongs in the standard rather than in one
vendor's namespace.

Only the **whole-model** `<dim>` takes one. The per-variable `<dim>` is a bare name
reference with nothing to document, and the two are told apart by structure: the
whole-model declaration is the one whose `<dim>` has `<elem>` children.

Position matters where the container uses `xs:sequence`: appending would force `<doc>`
after every other child, so it goes first, where documentation conventionally sits and
where `<doc>` already sits among a variable's children.

### The control parameters need no change at all

`<sim_specs>` corresponds to Vensim's `.Control` group, and its `<doc>` holds that
group's comment. `INITIAL TIME`, `FINAL TIME` and `TIME STEP` are ordinary equations
inside it, each with its own comment, so `<start>`, `<stop>` and `<dt>` need somewhere
to put one too — and change 1 has already provided it:

```xml
<sim_specs>
  <start vensim:doc="The initial time for the simulation.">0</start>
  <stop vensim:doc="The final time for the simulation.">100</stop>
  <dt vensim:doc="The time step.">0.25</dt>
</sim_specs>
```

A standard `doc` attribute was drafted here and then dropped. It would have had to be an
attribute rather than a `<doc>` child, because `<start>` and `<stop>` are `xs:double` and
simple content forbids child elements — a `<doc>` child means mixed content, and mixed
content cannot carry a simple type, so the three numbers that define the simulation run
would stop being validated as numbers. Having reached "an attribute, then", the vendor
namespace does the same job for nothing, and a control parameter's comment is not
something other tools need to read.

This is change 1 earning its keep in a place the corpus could not have predicted, which
is the argument in its own section for not scoping it too tightly.

Note that Vensim currently exports `<start>0<doc>…</doc></start>`, the shape item 4 cites
as evidence. That is not legal here and is not proposed; the exporter moves to
`vensim:doc`.

## 3. `<model_dimensions>` for the whole-model list

Two different elements are called `<dimensions>`, and the schema pays for it with a
workaround it documents in a comment: the whole-model list is declared **inline** inside
`<xmile>`, because XSD forbids two global elements with the same name and the per-variable
list holds the global slot. The comment has been there since the v1.0 schema.

They are not two spellings of one thing. The whole-model element holds **definitions**:
`<dim name="Region">` with `<elem>` children. The per-variable element holds
**references**: `<dim name="Region"/>`, name only.

Units already draw exactly this distinction, and draw it well:

| role | units | dimensions, before | dimensions, after |
|---|---|---|---|
| container of definitions | `<model_units>` | `<dimensions>` | `<model_dimensions>` |
| one definition | `<unit name="…">` | `<dim name="…">` | `<dim name="…">` |
| what a variable carries | `<units>` | `<dimensions>` | `<dimensions>` |

Three roles, three names. Dimensions had three roles and two names.

**The whole-model one is renamed, not the per-variable one**, which is the cheaper way
round by a wide margin: 64 occurrences in the corpus against 4,490. The spelling everybody
writes does not change.

```xml
<model_dimensions>
  <dim name="Region" size="2"><elem name="North"/><elem name="South"/></dim>
</model_dimensions>
...
<aux name="sales">
  <dimensions><dim name="Region"/></dimensions>
  <eqn>…</eqn>
</aux>
```

The deprecated spelling gets the same treatment as `<smile>`: the content model becomes a
named type, `<model_dimensions>` owns it, and the top-level `<dimensions>` becomes a
reference to the same type. One definition, so the two cannot drift, and every existing
file still validates — there is a test case for each.

Item 3 records what the collision costs and why it was avoidable. An earlier draft of this
change went the other way, adding `<dimension>` for the per-variable use; that renamed the
common form instead of the rare one, and borrowed Vensim's word "subscripts" before that.
`<model_dimensions>` is XMILE's own vocabulary and moves 64 elements instead of 4,490.

### Other overloads, left alone

`<dimensions>` is the worst case but not the only one, and the other two are not worth
disturbing:

- **`<units>`** is overloaded in practice rather than in the schema. The schema is clean —
  `<model_units>` holds definitions, `<unit>` is one definition, `<units>` is what a
  variable carries — but 42 elements in the corpus write `<units name="…"><eqn>…</eqn>
  </units>` inside `<model_units>`, where the schema says `<unit>`. All 42 come from one
  vendor's older exports, against 1,191 correct `<unit>` elements, and the newest files
  from that vendor get it right. That reads like a fixed bug, and legalising it would buy
  42 errors at the price of a permanent second spelling.
- **`<eqn>`** carries four meanings: the equation on a `<flow>` or `<aux>`, the
  *initial* equation on a `<stock>`, the initial equation for one array element under
  `<stock><element>`, and a units expression inside `<unit>`. Each is unambiguous in
  context, so this one slides.

[Item 16](../16-element-name-collisions.md) surveys all four with counts, and asks for the
one thing that would stop the list growing: a naming rule for future additions.

## 4. Requirements nobody meets

Four attributes are `use="required"` in the schema and largely or entirely absent from
real files. Counted over 122 models:

| Attribute | Written | Of |
|---|---:|---:|
| `plot/@title` | 204 | 1,538 |
| `table/@column_width` | 5 | 23 |
| `table/@report_interval` | 0 | 419 |
| `uses_arrays/@max_dimensions` | 0 | 13 |

All four become optional. `plot/@title` alone accounts for 1,258 of the errors removed,
which makes it the single most expensive requirement in the schema.

They go unwritten for two different reasons, and the two want different long-term
remedies.

**Three have a sensible default, so writing them conveys nothing.** `plot/@title`,
`table/@column_width` and `table/@report_interval` are display attributes. Every tool
already has a default for each — a plot with no title takes the name of the variable it
plots — so requiring them makes every file carry a value that says only what the reader
would have assumed. Optional with a documented default is the right shape, and that is
what this change does.

**One is derivable from the model itself.** `uses_arrays/@max_dimensions` is the maximum
dimensionality used by any variable, which a reader can count. It belongs to the
capability block, and item 11 argues that block should be deprecated outright rather than
relaxed: every fact the `<uses_*>` flags declare can be established by inspecting the file,
more cheaply and more reliably than by trusting a declaration that nothing keeps in step.

The corpus supports the stronger claim. Across 122 models the whole capability family
appears 16 times — `uses_arrays` 13, `uses_outputs` 3, and every other flag zero — and all
13 `uses_arrays` sit inside `<smile>` rather than `<options>`. `<uses_macros>`, which
carries two REQUIRED attributes of its own, never appears at all, though three files
contain `<macro>` elements. Relaxing `max_dimensions` legalises those 13; it does not
address the mechanism, which is item 11's business and not a schema change.

`uses_arrays` gains a second change for a different reason. Section 2 of the specification
calls the attribute `maximum_dimensions` and the schema calls it `max_dimensions`; no file
writes either. Both are accepted until the TC picks one, which is the honest state of
affairs rather than a silent choice.

A requirement no implementation meets is not a requirement. Note that item 9's five
REQUIRED `<view>` attributes are not here: those are required by the prose, not the
schema, so there is nothing in the XSD to relax.

## 5. `<smile>` as a synonym for `<options>`

`<smile>` heads essentially every file one vendor produces, appears in no version of the
specification, and draws 71 errors in the corpus.

It can be declared cleanly, and `<smile>` stays small: an annotation, a reference to the
`<options>` content model, and the legacy attributes. The specification of what a
capability block contains does not move into the deprecated element.

That requires naming the type. `<smile>` needs eleven attributes `<options>` does not
have, so it needs a type of its own, and a type can only be derived from a named one. The
`<options>` content model therefore becomes `complexType name="options_type"` immediately
below the element, which keeps its annotation and its place; what changes is that its
content model is named rather than anonymous.

**XSD offers no way to have both halves**, and the alternatives are worth stating since
this looks like a free choice and is not:

- A *substitution group* would leave `<options>` completely untouched and give `<smile>`
  the same content for nothing — but a substitution-group member cannot add attributes,
  and those eleven attributes are the entire reason `<smile>` needs its own type.
- *Copying* the content model into `<smile>` also leaves `<options>` untouched, at the
  cost of putting 250 lines of capability specification inside a deprecated element. That
  is the arrangement this avoids: `<smile>` is the thing being retired, and it should not
  become where the specification lives.

When `<smile>` is retired, delete its declaration. `options_type` can stay named — a
named type used once is ordinary — or be folded back inline, which is mechanical.

`<smile>` carries `defaultAttributesApply="false"` for the reason the base schema gives on
`<view>`: extending a type that already carries `vendor_attributes` would declare the
wildcard twice.

Real files write the capability flags both ways, so both work: as child elements, exactly
as `<options>` does, and as attributes. Measured over 107 `<smile>` elements:

```
version         107   always "1.0"
namespace        96   always "std, isee"
uses_arrays      37   "1" x22, "2" x13, "3" x2      <- a LEVEL, not a presence flag
uses_submodels   16   "" x16                        <- empty string means "present"
uses_conveyor     8   ""
uses_queue        1   ""
```

The `uses_arrays` level is the one place `<smile>` and `<options>` are not equivalent, and
the annotation says so: `<uses_arrays>` carries a presence flag and a dimension count,
where the attribute carries 1, 2 or 3. Porting one to the other loses information, which
is the unfinished part of item 11's transition plan.

The element is marked deprecated in its annotation. It is declared so that a decade of
existing files validate, not to encourage new ones.

## 6. `<license>` in `<header>`

An optional `<license>` with text content, an optional `spdx` identifier and an optional
`url`. `<copyright>` asserts ownership and says nothing about reuse; this says what
someone may do with the model.

The element name uses American spelling, matching `color` and `center` elsewhere in the
schema, and so does its annotation. Our prose spells the word "licence", as item 10 does;
that is a house-style difference, not an inconsistency to correct in the schema.

## 7. A dimension must say what it contains

`<dim name="Region"/>` is accepted today at the whole-model level, and it is
uninterpretable. A reader cannot know what the dimension contains: no elements are named,
and no size is given from which positional names would follow. Either is enough; neither
is not.

```xml
<xs:assert test="@size or elem" xpathDefaultNamespace="##targetNamespace"/>
```

XSD 1.1 can express that. XSD 1.0 could not state a co-occurrence constraint at all, which
is a small argument in favour of the version the specification has already adopted.

The assertion lands on the shared `model_dimensions_type`, so it governs
`<model_dimensions>` and the deprecated top-level `<dimensions>` alike — one definition,
one rule.

**This is the one change here that is not additive.** It makes the schema reject something
it currently accepts, so the guarantee the other six carry does not extend to it. The
evidence that it costs nothing is the corpus: across 122 models every whole-model `<dim>`
carries either `<elem>` children (63) or a `size` (76), and none carries neither. Three
test cases pin it down, two of which assert rejection — a check that only ever asks "is
this accepted now?" cannot test a restriction.

## What this does not touch

- `<netflow>` (item 2) needs semantics, not a schema slot, and is not a candidate for a
  minimally invasive change.
- `<ai_information>` and `ai_state` are a live proposal from another vendor. Declaring
  them is the TC's call, not ours.
- The graph, table and slider style attributes — about 13,800 of the remaining errors —
  are drift between the schema and what tools write (item 5). Fixing it means enumerating
  what belongs, which is a bigger and more contentious job than any of the above.
- Nothing is removed. Withdrawn 1.0 devices stay withdrawn; requirements are relaxed, not
  deleted.
- `<initial>` as an alternative to `<eqn>` on a stock, which
  [item 16](../16-element-name-collisions.md) proposes. That changes what writers should
  emit rather than repairing what the schema wrongly rejects, so it belongs in the text
  proposal, not here. The distinction is the line this whole revision stays on.

## One thing the checker found

Fixing an error lets a validator descend past it, so three files now report
`<parm default="0">` inside a `<macro>`. That attribute is allowed by no version of
XMILE; it was simply unreachable behind an earlier error. All three files' totals still
fell. The checker separates "revealed" from "regressed" for exactly this reason.

```sh
py -3.12 tools/v-generate/make_v11x_proposal.py

```

eleven per-change cases alone.
